# 8. Dynamic FLAT Path Resolution for EHRBase Compositions

Date: 2026-03-29

## Status

Accepted

## Context

Open CIS builds FLAT format compositions (JSON key-value maps) to submit clinical data to EHRBase. Each key is a path like `adverse_reaction_list/allergies_and_adverse_reactions/adverse_reaction_risk:0/severity_of_reaction|code`. These paths must exactly match the **web template** that EHRBase generates internally from the uploaded OPT (Operational Template).

### Problem

The CAVE feature (allergies & adverse reactions) was failing with `"Could not consume Parts"` errors from EHRBase. This error occurs when the FLAT JSON contains keys that don't match any node in the web template — EHRBase's `FlatJsonUnmarshaller` tracks which keys it successfully "consumes" and rejects any leftovers.

Multiple fix attempts were made:

| Attempt | Change | Result |
|---------|--------|--------|
| Remove `\|value` suffix from DV_TEXT fields | Correct per spec | Still failed |
| Fix path: `exclusion_-_global` → `exclusion_global` | Correct sanitization | Still failed |
| Add `ad_hoc_heading` intermediate section | Matches OPT structure | Still failed |
| Rename `substance` → `causative_agent` | Matched server template | Worked for this field |
| Remove language/encoding from exclusion_global | EHRBase v2 auto-populates | Still failed for other paths |
| Use DV_TEXT instead of DV_CODED_TEXT for severity | Try alternate type | Still failed |

### Root Cause

The FLAT path IDs were being **guessed from the OPT XML** in the repository, but the actual IDs come from the **web template** that EHRBase generates — and these can differ because:

1. **Template version mismatch**: The startup code skipped re-upload if the template already existed on EHRBase (`if template_id in existing: continue`). So even after the OPT was reformatted in the repo, EHRBase kept its old version with different node names.

2. **ID generation is opaque**: EHRBase's `OPTParser.buildId()` sanitizes archetype term names to FLAT IDs (`"Severity of reaction"` → `severity_of_reaction`), but the input names depend on archetype versions, name constraints, and template overlays — all of which can vary between the OPT file and what's on the server.

3. **No validation feedback loop**: There was no way to inspect the actual web template to see what paths EHRBase expected.

## Decision

We adopt a three-part approach:

### 1. Always Re-upload Templates on Startup

Remove the skip-if-exists check in `ensure_templates_registered()`. Always attempt to upload the OPT file. EHRBase returns 409 if the template is identical, which we handle gracefully. This ensures the server template stays in sync with the repo.

### 2. Dynamic Path Resolution via Web Template

Instead of hardcoding FLAT path IDs, resolve them at runtime by fetching the web template from EHRBase and searching for nodes by their archetype at-codes (e.g., `at0089` for severity, `at0002` for exclusion statement). This makes the code **self-correcting** — it adapts to whatever template version the server has.

The resolver:
- Fetches the web template via `GET /rest/ecis/v1/template/{templateId}`
- Searches the tree for nodes by at-code in their `aqlPath`
- Extracts the `id` field (which is the FLAT path segment)
- Caches results in memory (one fetch per template per process lifetime)
- Falls back to hardcoded defaults if EHRBase is unreachable

### 3. Debug Endpoint for Path Inspection

Add `GET /api/cave/debug/webtemplate` that returns:
- All web template FLAT paths with their RM types
- An example FLAT composition generated by EHRBase (via the ECIS example API)
- The resolved path IDs

This provides a feedback loop for diagnosing future path issues without reading EHRBase logs.

## Consequences

### Positive

- **Self-healing**: Path mismatches are resolved automatically by reading the authoritative source (the web template)
- **Debuggable**: The debug endpoint provides immediate visibility into what EHRBase expects
- **Resilient**: Template re-upload on startup prevents drift between repo and server
- **No guessing**: We no longer need to manually decode OPT XML to determine FLAT IDs

### Negative

- **Extra HTTP call**: The first CAVE operation per process requires fetching the web template (~one additional request, then cached)
- **Runtime dependency**: If EHRBase is down when the first CAVE operation happens, we fall back to hardcoded defaults (which may be wrong)
- **Complexity**: The path resolver adds a new module to understand and maintain

### Neutral

- The debug endpoint is available in all environments; consider removing or protecting it in production if security is a concern
- Template re-upload is idempotent but adds a small delay to startup

## References

- EHRBase `OPTParser.buildId()`: Converts node names to FLAT IDs via regex sanitization and lowercasing
- EHRBase `FlatJsonUnmarshaller`: Source of "Could not consume Parts" errors — reports all unrecognized FLAT keys
- [EHRBase Flat Format Docs](https://docs.ehrbase.org/en/latest/09_flat/index.html): FLAT paths are concatenated `id` fields from the web template hierarchy
